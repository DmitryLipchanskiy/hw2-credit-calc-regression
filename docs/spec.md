Объект тестирования (SUT) для ДЗ №2, вариант B4. Аннуитетный кредит: ставка, срок,
досрочное погашение, страховка.

Спецификация — **единственный источник ожидаемых значений** наравне с
[oracle.md](oracle.md). Реализация на TypeScript и эталонная реализация на Python пишутся
по этому документу независимо друг от друга, авторы не читают код друг друга.

Каждое требование имеет идентификатор `REQ-NN` и сформулировано так, чтобы по нему
можно было написать падающий тест.

## 1. Область

**Входит:** расчёт аннуитетного платежа, график платежей помесячно, частичное и полное
досрочное погашение в двух режимах, страховка в одном режиме, валидация ввода,
итоговые агрегаты, тонкий UI поверх ядра.

**Не входит** (сознательно урезано, см. `REPORT.md`):

- дифференцированный платёж;
- второй и третий режимы страховки (разово в тело кредита; ежемесячно % от первоначальной
  суммы) — три режима утроили бы матрицу кейсов;
- плавающая ставка, каникулы, реструктуризация;
- комиссии, налоговый вычет, мультивалютность.

Структуры данных проектируются так, чтобы второй режим страховки добавлялся расширением
перечисления, а не переписыванием — но в scope он не берётся.

## 2. Представление денег и округление

### REQ-01. Деньги — целые копейки

Все денежные величины во входе, внутри ядра и в выходе — **целое число копеек**
(`number`, целое, неотрицательное). Рубли существуют только в слое форматирования вывода.

*Проверяется:* для любого поля результата, помеченного как денежное,
`Number.isInteger(value) === true`.

### REQ-02. Арифметика над деньгами — целочисленная

Сложение, вычитание и сравнение денежных величин выполняются над целыми копейками.
Промежуточное представление в рублях с дробной частью запрещено.

*Проверяется:* мутация «умножить на 1.0 через рубли и вернуть обратно» ломает хотя бы
один тест на суммах, не кратных копейке.

### REQ-03. Единственное допустимое место для плавающей точки

Аннуитетный коэффициент — **безразмерная** величина и по определению иррационален:
целочисленно вычислить `(1 + i)^n` нельзя. Поэтому число с плавающей точкой допускается
**только** при вычислении месячной ставки `i` (REQ-11) и коэффициента `K` (REQ-12).

Результат умножения денежной величины на `i` или `K` **немедленно** приводится к целым
копейкам функцией округления из REQ-04. Хранение денежной величины как `float` между
двумя операциями запрещено.

> Это уточнение к требованию «никаких float в расчётах»: полностью целочисленный расчёт
> аннуитета потребовал бы длинной рациональной арифметики, что противоречит требованию
> «объект тестирования остаётся намеренно простым». Ограничение зафиксировано осознанно
> и вынесено в `REPORT.md`.

### REQ-04. Округление — half-up до копейки

Округление денежных величин: **half-up** — 0.5 копейки и выше округляется вверх.
Все денежные величины в этой задаче неотрицательны, поэтому «вверх» и «от нуля»
совпадают; поведение для отрицательных не определено и не используется.

*Проверяется:* `roundHalfUp(1.5) === 2`, `roundHalfUp(2.5) === 3`, `roundHalfUp(1.4999) === 1`.
Реализация через `Math.round` неприемлема без проверки: `Math.round(-1.5) === -1`,
а встроенное банковское округление в некоторых языках даёт `2.5 → 2`.

### REQ-05. Последний платёж — корректирующий

Последний платёж графика гасит остаток долга **ровно в ноль**. Его основная часть равна
остатку долга на начало последнего месяца, а не расчётной аннуитетной величине.

*Проверяется:* `balanceAfter` последней строки графика `=== 0`.

### REQ-36. Денежные сравнения — строгое равенство, допуски запрещены

Любое сравнение денежных величин — в целых копейках, на **строгое равенство**.

**Запрещено** в проверках любого уровня — unit, E2E, кросс-проверка TS ↔ Python, сверка
с [oracle.md](oracle.md):

- `toBeCloseTo`, `toBeWithin` и любые матчеры с параметром точности;
- `Math.abs(a − b) < ε` в любом виде;
- округление, усечение или форматирование величины **перед** сравнением;
- сравнение денег в рублях с дробной частью;
- `epsilon`, `delta`, `tolerance` как имена переменных в коде проверок.

**Обоснование.** REQ-03 допускает плавающую точку в одном месте. Расхождение в копейку —
ровно тот дефект, ради которого взят этот вариант задания («расхождение в рубль
на пятнадцати годах — это тысячи в сумме»). Допуск в сравнении проглотит его молча,
и весь смысл набора проверок пропадёт.

Требование механически контролируется pre-commit hook'ом — см. `CLAUDE.md`, правило 4.5.

*Проверяется:* `grep` по `tests/**` и `oracle/**` не находит ни одного из перечисленных
паттернов; hook блокирует коммит с ними.

## 3. Входные параметры и валидация

### REQ-06. Состав входа

| Поле | Тип | Единица | Диапазон |
|---|---|---|---|
| `amount` | integer | копейки | 1 000 000 … 10 000 000 000 (10 тыс. … 100 млн ₽) |
| `annualRatePercent` | number | % годовых | 0.00 … 100.00, не более 2 знаков после запятой |
| `termMonths` | integer | месяцы | 1 … 360 |
| `insurance` | объект \| `null` | — | см. REQ-07 |
| `earlyRepayments` | массив | — | см. REQ-08, может быть пустым |

### REQ-07. Параметры страховки

`insurance = { annualRatePercent }`, где `annualRatePercent` — число 0.00 … 10.00,
не более 2 знаков после запятой. `insurance === null` означает «страховки нет».

### REQ-08. Параметры досрочного погашения

Элемент массива: `{ month, amount, mode }`.

- `month` — integer, 1 … `termMonths`;
- `amount` — integer копеек, строго больше нуля;
- `mode` — `"reduceTerm"` (уменьшить срок) или `"reducePayment"` (уменьшить платёж).

В один месяц допускается **не более одного** досрочного погашения.

### REQ-09. Поведение на некорректном вводе

При некорректном вводе расчёт **не выполняется**, возвращается структурированная ошибка
с кодом. Исключения не бросаются, `NaN`, `Infinity` и частично заполненный результат
не возвращаются.

| Код | Условие |
|---|---|
| `AMOUNT_NOT_INTEGER` | `amount` не целое |
| `AMOUNT_OUT_OF_RANGE` | `amount` вне диапазона REQ-06 |
| `RATE_OUT_OF_RANGE` | `annualRatePercent` вне 0 … 100 |
| `RATE_TOO_PRECISE` | у ставки больше 2 знаков после запятой |
| `TERM_NOT_INTEGER` | `termMonths` не целое |
| `TERM_OUT_OF_RANGE` | `termMonths` вне 1 … 360 |
| `NOT_A_NUMBER` | любое числовое поле — `NaN`, `Infinity`, `null`, строка, `undefined` |
| `INSURANCE_RATE_OUT_OF_RANGE` | ставка страховки вне 0 … 10 |
| `EARLY_MONTH_OUT_OF_RANGE` | `month` вне 1 … `termMonths` |
| `EARLY_AMOUNT_NOT_POSITIVE` | `amount` досрочки ≤ 0 или не целое |
| `EARLY_MODE_UNKNOWN` | `mode` не из двух допустимых значений |
| `EARLY_DUPLICATE_MONTH` | два досрочных погашения в одном месяце |

### REQ-10. Ошибки возвращаются все сразу

Если некорректны несколько полей, возвращаются **все** соответствующие коды, а не только
первый. Порядок кодов в списке соответствует порядку полей в таблице REQ-09.

*Проверяется:* вход с отрицательной суммой и сроком 400 даёт ровно два кода.

## 4. Расчёт базового аннуитета

### REQ-11. Месячная ставка

`i = annualRatePercent / 100 / 12`. Без округления (см. REQ-03).

### REQ-12. Аннуитетный коэффициент и платёж

При `i > 0`:

```
K = i * (1 + i)^n / ((1 + i)^n − 1)
payment = roundHalfUp(amount * K)
```

где `n` — число оставшихся месяцев, `amount` — остаток долга в копейках.

### REQ-13. Нулевая ставка и граница ветвления

При `annualRatePercent === 0` формула REQ-12 неприменима (деление на ноль).
В этом случае `payment = roundHalfUp(amount / n)`.

**Граница ветвления строгая.** Ветка нулевой ставки выбирается **только** при
`annualRatePercent === 0`. Любое ненулевое значение, включая минимальное допустимое,
идёт по REQ-12. Условие вида `rate < 0.01`, `rate <= 0` или `!rate` — ошибка.

*Проверяется двумя кейсами:*

1. кредит 120 000 ₽ на 12 месяцев под **0 %** — платёж ровно 10 000,00 ₽,
   `totalInterest === 0`, `overpayment === 0`;
2. тот же кредит под **0.01 %** — идёт по REQ-12, `totalInterest > 0` (строго больше нуля,
   пусть и на копейки). Ветка нулевой ставки не должна сработать.

> **Ограничение диапазона.** Минимальная ненулевая ставка, которую можно подать на вход, —
> **0.01 %**: REQ-06 разрешает не более двух знаков после запятой, поэтому 0.0001 %
> отвергается кодом `RATE_TOO_PRECISE` и граничным кейсом для этой ветки быть не может.
> Если нужен более тонкий шаг ставки, менять надо REQ-06, и это отдельное решение.

### REQ-14. Структура строки графика

Каждая строка графика содержит:

| Поле | Тип | Описание |
|---|---|---|
| `month` | integer | номер месяца, с 1 |
| `paymentTotal` | копейки | `principal + interest + insurance`; досрочка сюда **не входит** |
| `interest` | копейки | проценты за месяц |
| `principal` | копейки | погашение тела регулярным платежом |
| `insurance` | копейки | страховая премия месяца, 0 если не начисляется |
| `earlyRepaymentRequested` | копейки | сколько просили внести досрочно, 0 если досрочки нет |
| `earlyRepaymentApplied` | копейки | сколько **фактически** списано в счёт тела |
| `earlyRepaymentExcess` | копейки | `requested − applied`, см. REQ-23 |
| `balanceAfter` | копейки | остаток после регулярного платежа и досрочки |

Все денежные поля — целые копейки, неотрицательные.

### REQ-15. Порядок вычислений внутри месяца

Строго в этом порядке:

1. `interest = roundHalfUp(balanceBefore * i)`;
2. `principal = payment − interest`;
3. если `principal > balanceBefore`, то `principal = balanceBefore` (последний месяц);
4. `insurance` — по REQ-17, считается от `balanceBefore`;
5. `paymentTotal = principal + interest + insurance` — досрочка сюда не входит;
6. `balanceAfter = balanceBefore − principal`;
7. досрочное погашение месяца, если оно есть, — по REQ-20 и REQ-23, применяется
   **после** шага 6 и уменьшает `balanceAfter`;
8. пересчёт параметров на оставшийся срок — по REQ-21 (`reduceTerm`)
   или REQ-22 (`reducePayment`), только если шаг 7 что-то списал и кредит не закрыт.

*Проверяется:*

- мутация «считать проценты от `balanceAfter` вместо `balanceBefore`» ломает тесты
  на первом же месяце;
- мутация «поменять местами шаги 6 и 7» (внести досрочку до регулярного платежа) меняет
  `interest` месяца `M` — падает тест на конкретное значение процентов (REQ-20).

### REQ-16. Инварианты графика

Выполняются **всегда**, при любых допустимых входных параметрах. Каждый инвариант имеет
собственный стабильный идентификатор `INV-NN` — на него ссылаются тесты агентов C и D
и записи в [decisions.md](decisions.md).

Инварианты проверяются на **каждом** кейсе набора, а не отдельным тестом: это не сценарий,
а свойство. Реализуются одной общей функцией-проверяльщиком, вызываемой из каждого кейса.

| ID | Инвариант | Что ловит |
|---|---|---|
| **INV-01** | `sum(principal) + sum(earlyRepaymentApplied) === amount` — тело кредита погашено ровно, без недостачи и излишка | ошибки округления, потерянную копейку |
| **INV-02** | `balanceAfter` последней строки `=== 0` | некорректный корректирующий платёж (REQ-05) |
| **INV-03** | `balanceAfter` монотонно не возрастает по месяцам | отрицательное погашение, рост долга |
| **INV-04** | для каждой строки `paymentTotal === principal + interest + insurance` | попадание страховки или досрочки не в своё поле |
| **INV-05** | `1 ≤ actualTermMonths ≤ termMonths`, номера месяцев идут подряд от 1 без пропусков | off-by-one в числе периодов |
| **INV-06** | для каждой строки `interest ≥ 0`, **`principal ≥ 0`**, все денежные поля целые и `≥ 0` | отрицательные величины, float |
| **INV-07** | для каждой строки `earlyRepaymentApplied + earlyRepaymentExcess === earlyRepaymentRequested` | потерю денег при полном досрочном погашении (REQ-23) |
| **INV-08** | `totalPaid === totalPrincipal + totalInterest + totalInsurance` | смешение статей в итогах |

Все сравнения — строгое равенство целых копеек (REQ-36).

> **Правка INV-06, версия 1.2 (`D-23`).** Было `principal > 0`, стало `principal ≥ 0`.
> Строгая положительность не выводится из требований: когда
> `roundHalfUp(B·K) === roundHalfUp(B·i)`, платёж покрывает только проценты, тело
> не гасится вовсе, и весь долг закрывается корректирующим последним платежом (REQ-05).
> Обнаружено независимо агентами A и B. Закрытие кредита по-прежнему удерживает INV-02 —
> отдельного требования не заводится.

## 5. Страховка

### REQ-17. Момент и база начисления

Страховая премия начисляется в месяцах `1, 13, 25, 37, …` (первый месяц и далее каждые 12).
База — **остаток долга на начало месяца** (`balanceBefore`).

```
insurance = roundHalfUp(balanceBefore * insuranceAnnualRatePercent / 100)
```

В остальные месяцы `insurance = 0`.

### REQ-18. Страховка не влияет на погашение

Страховая премия:

- **не** увеличивает тело кредита;
- **не** участвует в начислении процентов;
- **не** уменьшает основной долг;
- увеличивает только `paymentTotal` того месяца, в котором начислена.

*Проверяется:* при включении страховки график погашения основного долга (`principal`,
`interest`, `balanceAfter` по месяцам) **побайтово совпадает** с графиком без страховки.
Это ключевая проверка против мутации «игнорировать страховку» и против обратной ошибки
«страховка попала в тело».

### REQ-19. Страховка после закрытия кредита

Если кредит закрыт досрочно, страховка за последующие годовые периоды **не начисляется**.
В месяце полного погашения страховка начисляется, если этот месяц попадает в ряд
`1, 13, 25, …`.

## 6. Досрочное погашение

### REQ-20. Момент применения

Досрочная сумма вносится **после** регулярного платежа месяца `M` (шаг 7 в REQ-15)
и уменьшает остаток долга напрямую, без начисления на неё процентов.

```
balanceAfter = balanceAfter − earlyRepaymentApplied
```

где `earlyRepaymentApplied` определяется по REQ-23.

*Проверяется:* мутация «вносить досрочку до начисления процентов» меняет `interest`
месяца `M` — тест на конкретное значение процентов падает.

### REQ-21. Режим «уменьшить срок»

`mode = "reduceTerm"`: размер регулярного платежа **не меняется**. Число оставшихся
месяцев пересчитывается исходя из нового остатка и неизменного платежа. Фактический срок
кредита сокращается.

*Проверяется:* `payment` строк после месяца `M` равен `payment` строк до него;
число строк графика меньше `termMonths`.

### REQ-22. Режим «уменьшить платёж»

`mode = "reducePayment"`: число оставшихся месяцев **не меняется** (`termMonths − M`).
Регулярный платёж пересчитывается по REQ-12 от нового остатка на оставшийся срок.

*Проверяется:* число строк графика равно `termMonths`; `payment` после месяца `M` строго
меньше, чем до него.

### REQ-23. Полное досрочное погашение и излишек

Пусть `B` — остаток долга после регулярного платежа месяца `M`, `R` — запрошенная
досрочная сумма (`earlyRepaymentRequested`).

```
earlyRepaymentApplied = min(R, B)
earlyRepaymentExcess  = R − earlyRepaymentApplied
```

Если `R ≥ B`, кредит закрывается в месяце `M`: `balanceAfter === 0`, строк после месяца `M`
в графике нет.

**Излишек — отдельная величина, а не исчезнувшие деньги.** Он фиксируется в поле
`earlyRepaymentExcess` строки и агрегируется в `totalEarlyRepaymentExcess` (REQ-26).
Излишек **не** входит ни в `totalPaid`, ни в `totalPrincipal`: в счёт кредита он
не пошёл. Что с ним происходит в реальном банке — возврат на счёт, зачисление в следующий
платёж — за границей этой спецификации; калькулятор обязан лишь показать его величину.

*Проверяется:*

- при `R > B`: `earlyRepaymentApplied === B`, `earlyRepaymentExcess === R − B`,
  `balanceAfter === 0`, `actualTermMonths === M`;
- при `R === B`: то же, но `earlyRepaymentExcess === 0`;
- при `R < B`: `earlyRepaymentApplied === R`, `earlyRepaymentExcess === 0`,
  график продолжается;
- во всех трёх случаях выполняется INV-07 и INV-01.

Прежняя формулировка «излишек не возвращается» заменена: она описывала исчезновение денег
и была непроверяемой — тест не отличал бы «списали ровно остаток» от «списали всё».
См. `D-04` в [decisions.md](decisions.md).

### REQ-24. Несколько досрочных погашений

Досрочные погашения применяются в порядке возрастания месяца. Каждое следующее считается
от состояния, полученного после предыдущего. Режимы могут смешиваться.

### REQ-25. Досрочка после фактического закрытия

Если кредит уже закрыт (досрочно) к моменту месяца `M`, досрочное погашение за месяц `M`
**игнорируется**.

Результат содержит поле `ignoredEarlyRepayments` — **список записей**, не флаг и не булево:

```
ignoredEarlyRepayments: Array<{ index, month, amount }>
```

- `index` — позиция погашения в исходном входном массиве `earlyRepayments`;
- `month`, `amount` — его параметры.

Если проигнорированных нет, поле — пустой массив, а не `null` и не `undefined`.

**Тест обязан проверять, какие именно погашения проигнорированы**, а не сам факт наличия
проигнорированных. Проверка вида `ignoredEarlyRepayments.length > 0` недостаточна:
она не отличит «проигнорировали то, что надо» от «проигнорировали не то».

Это **не ошибка валидации**: на входе `month ≤ termMonths` был корректен, невозможность
выяснилась только в ходе расчёта.

*Проверяется:* кейс с тремя досрочными погашениями, где второе закрывает кредит целиком, —
`ignoredEarlyRepayments` содержит ровно одну запись, с `index === 2` и месяцем третьего
погашения.

## 7. Итоговые агрегаты

### REQ-26. Состав итогов

| Поле | Определение |
|---|---|
| `monthlyPayment` | первый регулярный платёж **без страховки**, копейки |
| `actualTermMonths` | фактическое число строк графика |
| `totalPrincipal` | `sum(principal) + sum(earlyRepaymentApplied)` |
| `totalInterest` | `sum(interest)` — **только проценты** |
| `totalInsurance` | `sum(insurance)` — **только страховые премии** |
| `totalPaid` | `sum(paymentTotal) + sum(earlyRepaymentApplied)` |
| `totalEarlyRepaymentExcess` | `sum(earlyRepaymentExcess)`, REQ-23; **не входит** в `totalPaid` |
| `overpayment` | `totalInterest + totalInsurance` |
| `ignoredEarlyRepayments` | список записей по REQ-25 |

### REQ-27. Согласованность итогов

- `totalPrincipal === amount`;
- `totalPaid === totalPrincipal + totalInterest + totalInsurance` (INV-08);
- `overpayment === totalPaid − amount`.

Проверяется на **каждом** кейсе набора, а не отдельным тестом: это инвариант.

### REQ-37. Проценты и страховка — раздельно и неслиянно

`totalInterest` и `totalInsurance` — **разные поля результата**. Единой величины
«переплата», из которой нельзя выделить составляющие, в результате не существует:
`overpayment` — производное поле, а не источник.

Требование к реализации: страховая премия не попадает в `interest` ни на одной строке
графика, а проценты не попадают в `insurance`.

**Проверяется парой кейсов** (это же ловит мутацию «страховка попала в проценты»):

взять два расчёта с одинаковыми `amount`, `annualRatePercent`, `termMonths`,
`earlyRepayments` и различающиеся только наличием страховки. Тогда:

- `totalInterest` **строго совпадает** в обоих расчётах;
- `totalInsurance === 0` в первом и `> 0` во втором;
- `overpayment` различается ровно на `totalInsurance` второго.

Первое утверждение — ключевое: если страховка утекла в проценты, `totalInterest`
разъедется, и тест упадёт. Это агрегатное дополнение к REQ-18, который проверяет то же
свойство построчно.

## 8. Пользовательский интерфейс

Тонкий слой поверх ядра. Vanilla HTML + CSS + один `.js`, собранный из TS без сборщика
(`tsc` в `dist/`), без фреймворков.

### REQ-28. Поля формы

Форма содержит: сумма (₽), ставка (% годовых), срок (месяцев), чекбокс страховки
со ставкой, блок добавления досрочных погашений (месяц, сумма, режим).

### REQ-29. Пересчёт

Результат пересчитывается по нажатию кнопки «Рассчитать». Автопересчёт по вводу
не реализуется — он создаёт гонки в E2E-тестах.

### REQ-30. Вывод результата

Выводятся: ежемесячный платёж, фактический срок, общая сумма выплат, переплата,
и таблица графика помесячно. Денежные величины форматируются как `1 234 567,89 ₽`
(неразрывный пробел как разделитель тысяч, запятая как десятичный разделитель).

### REQ-31. Отображение ошибок

При некорректном вводе таблица графика **не отображается**, вместо неё выводится список
сообщений об ошибках. Каждое сообщение имеет `data-error-code` с кодом из REQ-09 —
чтобы E2E-тест проверял код, а не текст сообщения.

### REQ-32. Тестопригодность разметки

Все элементы, с которыми взаимодействуют тесты, имеют атрибут `data-testid`.
Селекторы по классам и позиции в DOM в тестах не используются.

### REQ-33. Оформление

Адаптивная вёрстка (один брейкпоинт, 768px), поддержка тёмной темы через
`prefers-color-scheme`, весь CSS — в одном файле. Без изображений и внешних шрифтов.

## 9. Публичный контракт ядра

### REQ-38. Контракт фиксируется спецификацией, а не реализацией

Сигнатуры и имена полей задаются **здесь** и одинаковы для всех участников веера:
реализация (агент A), эталон (агент B), оба набора проверок (агенты C и D).

**Причина.** Если бы контракт определял автор реализации, агентам C и D пришлось бы
прочитать его код, чтобы узнать имена полей, — и независимость проверки, ради которой
построена вся схема, исчезла бы ещё до первого теста. Контракт — часть спецификации,
а не часть реализации.

```ts
// src/core/types.ts

/** Денежная величина. Всегда целое число копеек, неотрицательное. REQ-01. */
export type Kopecks = number;

export type EarlyRepaymentMode = 'reduceTerm' | 'reducePayment';

export interface EarlyRepaymentInput {
  month: number;              // 1 … termMonths
  amount: Kopecks;            // > 0
  mode: EarlyRepaymentMode;
}

export interface InsuranceInput {
  annualRatePercent: number;  // 0.00 … 10.00, не более 2 знаков
}

export interface CreditInput {
  amount: Kopecks;
  annualRatePercent: number;  // 0.00 … 100.00, не более 2 знаков
  termMonths: number;         // 1 … 360
  insurance: InsuranceInput | null;
  earlyRepayments: EarlyRepaymentInput[];
}

/** Коды из таблицы REQ-09. */
export type ValidationCode =
  | 'AMOUNT_NOT_INTEGER'
  | 'AMOUNT_OUT_OF_RANGE'
  | 'RATE_OUT_OF_RANGE'
  | 'RATE_TOO_PRECISE'
  | 'TERM_NOT_INTEGER'
  | 'TERM_OUT_OF_RANGE'
  | 'NOT_A_NUMBER'
  | 'INSURANCE_RATE_OUT_OF_RANGE'
  | 'EARLY_MONTH_OUT_OF_RANGE'
  | 'EARLY_AMOUNT_NOT_POSITIVE'
  | 'EARLY_MODE_UNKNOWN'
  | 'EARLY_DUPLICATE_MONTH';

/** Строка графика. Состав полей — REQ-14. */
export interface ScheduleRow {
  month: number;
  paymentTotal: Kopecks;
  interest: Kopecks;
  principal: Kopecks;
  insurance: Kopecks;
  earlyRepaymentRequested: Kopecks;
  earlyRepaymentApplied: Kopecks;
  earlyRepaymentExcess: Kopecks;
  balanceAfter: Kopecks;
}

/** REQ-25. */
export interface IgnoredEarlyRepayment {
  index: number;   // позиция в исходном массиве earlyRepayments
  month: number;
  amount: Kopecks;
}

/** Итоги. Состав — REQ-26. */
export interface CreditTotals {
  monthlyPayment: Kopecks;
  actualTermMonths: number;
  totalPrincipal: Kopecks;
  totalInterest: Kopecks;
  totalInsurance: Kopecks;
  totalPaid: Kopecks;
  totalEarlyRepaymentExcess: Kopecks;
  overpayment: Kopecks;
  ignoredEarlyRepayments: IgnoredEarlyRepayment[];
}

export type CalculationResult =
  | { ok: true;  schedule: ScheduleRow[]; totals: CreditTotals }
  | { ok: false; errors: ValidationCode[] };
```

```ts
// src/core/index.ts

/** Единственная точка входа ядра. Исключений не бросает (REQ-09). */
export function calculateCredit(input: CreditInput): CalculationResult;

/** Округление half-up до целых копеек. REQ-04. */
export function roundHalfUp(value: number): Kopecks;
```

**Дискриминатор результата — поле `ok`.** Проверка вида `'errors' in result` допустима,
но канонический способ — `result.ok === false`.

**Порядок кодов в `errors`** — по порядку полей в таблице REQ-09 (REQ-10).

**Эталон на Python** воспроизводит те же имена полей в `snake_case`
(`payment_total`, `early_repayment_applied`, `total_insurance` и так далее) и возвращает
словарь той же структуры. Сопоставление имён — механическое, выполняется скриптом сверки.

## 10. Что считается «прогоном»

### REQ-34. Одна команда

`npm test` запускает весь набор: unit-уровень поверх ядра и E2E поверх формы.
Отдельная команда не требуется. Вывод содержит итог passed / failed / skipped
и общее число тестов.

### REQ-35. Артефакты прогона

HTML-репортер Playwright, трейс и скриншот на падениях. Зафиксированная копия отчёта
для сдачи кладётся в `reports/`.
