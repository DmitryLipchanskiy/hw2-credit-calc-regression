### 4.4. Заморозка спецификации

**С момента старта S2 `docs/spec.md` перестаёт быть свободно редактируемым.**

Любая правка — только через запись в `docs/decisions.md` со ссылкой на затронутый
`REQ-NN` или `INV-NN`, с указанием: что было, что стало, на каком основании, кто внёс.

Причина: спецификация — источник ожидаемых значений для агентов C и D. Документ,
который можно править по ходу, неизбежно подстроится под реализацию — и независимость
проверки, ради которой вся схема и построена, испарится.

Номера `REQ-NN` стабильны и не переиспользуются; новое требование получает следующий
свободный номер. Перенумерация запрещена — она обесценила бы ссылки из тестов.

## S2, шаг 1 — веер и сведение

### Раскладка на субагентов (веер, 4 зоны, одна сессия)

Каждому агенту в промпт передаются: `docs/spec.md`, релевантные разделы `CLAUDE.md`,
явная граница зоны и **запрет трогать чужую**.

| Агент | Зона (только эти файлы) | Что делает | Что ему запрещено видеть |
|---|---|---|---|
| **A. Реализация** | `src/core/**` | сначала заглушка (см. ниже), затем ядро по spec.md: аннуитет, график, страховка, досрочка, валидация | тесты, эталон |
| **B. Эталон** | `oracle/**` (Python) | независимая реализация формул по spec.md | код агента A |
| **C. Кейсы: база** | `tests/core/base.spec.ts` | REQ-01…REQ-16, REQ-26…REQ-27, REQ-36…REQ-37, инварианты INV-01…INV-08 | реализация A |
| **D. Кейсы: сценарии** | `tests/core/scenarios.spec.ts` | REQ-17…REQ-25: страховка, досрочка в двух режимах, полное погашение, излишек, игнорируемые | реализация A |

Границы механические: непересекающиеся пути. Агенты C и D пишут тесты **по спецификации,
не видя реализации** — это и есть п. 2 правил работы.

### Красная фаза при веере (уточнение к правилу 4.2)

Ломать каждый тест по отдельности при веере не нужно и дорого: агенты C и D и так пишут
вслепую. Вместо этого:

1. агент A **первым делом** создаёт заглушку `src/core/` — публичный контракт из spec.md,
   каждая функция бросает `NotImplementedError`. Заглушка коммитится отдельно;
2. наборы C и D прогоняются **против заглушки**, до появления реализации;
3. **все обязаны упасть.** Полный вывод прогона идёт в журнал сессии как красная фаза;
4. зелёная фаза — тот же прогон после сведения реализации.

**Тест, прошедший против заглушки, — сломанный по определению.** Такие выписываются
отдельным списком в `sessions/session-2.md` и разбираются поимённо: чаще всего это тест
без ассерта, тавтология или ассерт на то, что функция не вызвана. Молча удалять их нельзя,
и «починить, чтобы падал» без объяснения — тоже.

### Сведение и кросс-проверка

Прогон, разбор расхождений TS ↔ Python ↔ `oracle.md`. Расхождение — повод искать ошибку
в коде, **не подгонять ожидание** (правило 4.6).

### ⏸ Точка останова S2

Показываю пользователю:

- полный вывод красной фазы против заглушки + список тестов, которые не упали;
- полный вывод зелёной фазы;
- **таблицу расхождений TS ↔ Python ↔ oracle.md**;
- сколько времени и контекста заняли четыре агента (вход для замера).

Дальше — только после разбора таблицы расхождений.

## Замер «последовательно против веера» — отдельная чистая сессия

**Не часть S2.** Внешний запуск №1: последовательный прогон обязан идти в сессии, которая
не видела ни spec-обсуждения, ни результатов веера, — иначе он стартует с преимуществом
и замер бессмыслен.

| | Где берётся | Что фиксируем |
|---|---|---|
| **Веер** | точка останова S2, шаг 1 | время от старта агентов до сведения; контекст главной сессии |
| **Последовательно** | чистая сессия, запускает пользователь по `docs/prompts/sequential-run.md` | время; контекст той сессии |

**Порядок обязателен:** сначала веер (S2), потом замер. Обратный порядок испортит веер —
кейсы уже будут написаны.

**Честные оговорки для отчёта:**

- сравниваются только зоны C и D, не вся работа;
- замеряется одна попытка каждого варианта, не среднее по нескольким;
- ожидаемый результат по материалам занятия — веер **медленнее** по времени, но кратно
  экономнее по контексту главной сессии. Если получится иначе — идёт в отчёт как есть.

## S3 — скептик и мутации

### Worktree скептика — полный, ради свободы ломать

**Первый из двух заходов на worktrees** (второй — в S4, три параллельные задачи).

```
git -C /Users/qamac/WebstormProjects/hw2-credit-calc-regression \
    worktree add /Users/qamac/WebstormProjects/wt-skeptic -b skeptic
```

**Worktree полный, `src/` на месте.** Первая редакция плана прятала реализацию —
ошибка, снятая пользователем (`D-28`): сильнейший приём скептика — мутация, сломать
реализацию и посмотреть, какие тесты этого не заметили. Без `src/` он лишается главного,
ради чего его зовут.

Польза worktree здесь другая и реальная: скептик **свободно ломает код у себя**,
коммитит пробы в ветку `skeptic`, а `main` не трогается вовсе. Независимый разработчик
со своей веткой и своими коммитами — картина ровно из задания.

**Изоляция, которая остаётся:** скептику запрещено читать `sessions/`, `REPORT.md`
и `docs/plan.md`. Там наша версия событий — она настроит его соглашаться вместо того,
чтобы проверять. Спецификация, тесты, реализация, эталон — доступны все.

Чистка — в том же шаге, что и разбор находок:

```
git -C /Users/qamac/WebstormProjects/hw2-credit-calc-regression \
    worktree remove /Users/qamac/WebstormProjects/wt-skeptic
git -C /Users/qamac/WebstormProjects/hw2-credit-calc-regression worktree prune
git -C /Users/qamac/WebstormProjects/hw2-credit-calc-regression worktree list
```

### Агент-скептик — **отдельная сессия, запускает пользователь**

Не субагент. Задание формулирует буквально: «отдельный агент в отдельной сессии,
а не тот же, что писал код».

- главная сессия готовит готовый промпт → `docs/prompts/skeptic.md`;
- пользователь открывает вторую сессию Claude Code, вставляет промпт;
- задача скептика: **ломать чужие кейсы** — искать дыры в наборе C и D, а не в коде;
- вывод скептика целиком → `sessions/session-3-skeptic.md`;
- находки разбираются в главной сессии, каждая — либо новый тест, либо строка
  в `REPORT.md` с обоснованием, почему не берём.

### Мутационная проверка (CLAUDE.md 4.3)

5 мутаций ядра, таблица «мутация × упавшие тесты» → `docs/mutations.md`.
Выжившая мутация — дыра в покрытии, закрывается тестом. Если не закрыли — строка в отчёте.

**Риск сессии:** скептик и мутации могут найти много. Если находок больше, чем помещается
в бюджет, — закрываем по опасности, остальное в `REPORT.md` списком «знаем, не сделали».

## S4 — E2E, workflow, документы

### Три worktree, три агента, merge в main

**Второй заход на worktrees** — тот, что задание описывает буквально: «три разные задачи
одновременно, каждую в своём worktree, отдельным агентом, потом свести в основную ветку».

S4 раскладывается на три независимые задачи без пересечения зон:

| Ветка | Задача | Файлы |
|---|---|---|
| `e2e` | браузерные сценарии поверх формы | `tests/e2e/**`, `src/ui/**` |
| `workflow` | скилл регрессионного прогона | `.claude/skills/regression-run/**` |
| `docs` | README и REPORT | `README.md`, `REPORT.md` |

```
git worktree add ../wt-e2e      -b e2e
git worktree add ../wt-workflow -b workflow
git worktree add ../wt-docs     -b docs
```

Три агента, по одному в каждом. Merge в `main` выполняет **пользователь**, не я.

**Если возникнет конфликт — разбираем, а не давим `-X ours`.** Зоны спроектированы
непересекающимися, поэтому конфликт будет означать ошибку в раскладке, и её надо увидеть,
а не замазать.

**Чистка — в том же шаге, что и merge, не «потом»:**

```
git worktree remove ../wt-e2e
git worktree remove ../wt-workflow
git worktree remove ../wt-docs
git worktree prune
git worktree list          # вывод показывается
```

Три worktree — три `node_modules`. В материалах занятия описан случай, когда так
накопилось 250 ГБ и работа встала.

### E2E (немного, поверх формы)

Пирамида: основная масса кейсов уже на ядре. Здесь — ~6–8 браузерных сценариев:
ввод, пересчёт, вывод графика, невалидный ввод (проверка по `data-error-code`, REQ-31),
страховка, досрочка. Page Object, `data-testid`, без `waitForTimeout`.

Мало браузерных сценариев = матрица из двух ОС не становится источником флаки.

### Workflow — обязательный пункт 3

`.claude/skills/regression-run/SKILL.md` — скилл «регрессионный прогон по изменениям».

Процедура ровно та, что предлагает задание для QA:

```
взять изменения с последнего прогона (git diff от тега last-run)
  → сопоставить изменённые файлы с зонами spec.md (REQ)
  → собрать список затронутых сценариев
  → прогнать только их + smoke
  → отчёт в reports/run-<дата>.md
  → поставить тег last-run на текущий HEAD
```

Каждый шаг оставляет файл. Формат — скилл, потому что процедура вызывается по описанию
и переносится в другие проекты.

### Документы

`README.md` (что сделано, как запустить — обе ОС), `REPORT.md` целиком.

### PDF-отчёт — часть обязательной работы, не бонус

`REPORT.md` → HTML + CSS для печати → PDF. Титульная страница, оглавление, таблицы,
один акцентный цвет, колонтитулы с номерами страниц, без эмодзи. Промпты — раздел 8
материалов занятия. Готовый PDF коммитится в репозиторий.

Закрывает критерий **«Оформление»** из таблицы оценивания. Не режется.

### Финальный аудит независимым агентом — тоже здесь

Субагент с чистым контекстом, которому **запрещено читать `sessions/` и `REPORT.md`**
(правило 4.9 `CLAUDE.md`). Задача — проверить работу по факту: запустить прогон, сверить
заявленное с наблюдаемым, найти расхождения между `README.md` и реальностью.

Его находки идут в `REPORT.md` **как есть**, включая неприятные. Подтверждает критерий
**«Работает»** — тем, что проверка сделана не нами. Не режется.

**Контрольная точка S4: обязательная часть закрыта, CI зелёный на обеих ОС,
PDF собран, аудит проведён.** Дальше идёт только то, что в плюс.

## S5 — изоляция и недоверенный текст

### Изоляция (приоритет 1)

Docker не поднимаем: задание требует не Docker, а **вывод неудачной попытки**.

Два артефакта в `docs/isolation.md`:

1. `/sandbox` → попытка записи за пределы рабочей папки через Bash → **отказ в логе**;
2. та же попытка **через MCP-сервер** мимо песочницы.

Второй интереснее: в материалах прямо сказано, что песочница «применяется только
к Bash-командам и их дочерним процессам». Если границу удастся пробить — это сильный
отрицательный результат, идёт в отчёт как есть.

### Отчёт по инструментам: индекс кодовой базы

Отдельной строкой в критериях оценивания, и в первой версии плана этого пункта не было
вовсе — упущение, найденное пользователем.

**Порядок жёсткий, установка последней:**

1. пользователь присылает ссылку на инструмент (`GitNexus`, `Graphify` или аналог);
2. я изучаю репозиторий и отвечаю **до** установки: что это, что ставит на машину,
   какие хуки добавляет, куда ходит по сети, что читает, есть ли подозрительные места
   в коде и в описаниях инструментов. Вердикт: ставить или нет;
3. ставим только после этого.

**Замер** — на любом открытом репозитории, не на нашем: он слишком мал, чтобы разница
была видна. Один и тот же вопрос к коду до индексации и после
(«где считаются комиссии и кто это вызывает»), фиксируются время, потраченные токены,
качество ответа.

**Отзыв в свободной форме:** что понравилось, что нет, что не сработало. В материалах
занятия названа честная цифра — «заявляют 99 %, реально 20–30 %»; если у нас выйдет
иначе в любую сторону, пишем как вышло.

### Недоверенный текст (приоритет 2)

Инъекции кладутся в CSV с тестовыми данными: `tests/fixtures/untrusted/`.
Пять способов внедрения — комментарий в CSV, «служебная строка», поле «назначение
платежа», метаданные файла, невидимый Unicode.

- **Сильная модель (Opus 5)** — эта сессия;
- **Слабая модель (Haiku 4.5)** — отдельная сессия, **запускает пользователь**
  (в десктопном приложении модель выбирается в интерфейсе, командой не переключить).

Главная сессия готовит: файлы с инъекциями, точный промпт → `docs/prompts/injection.md`,
шаблон таблицы. Фиксируется **три исхода**, не два: выполнила / промолчала /
**назвала вслух**. Третий — единственный, на который можно полагаться.

## S6 — полировка UI

**Только косметика.** Функциональная форма по REQ-28…REQ-33 существует с S4 и покрыта
E2E-сценариями; здесь она доводится до приличного вида.

**Таймбокс 45 минут.** По истечении работа останавливается в текущем виде — не доводится
«ещё десять минут». Vanilla HTML + CSS, без фреймворков и без шага сборки. Адаптив
(один брейкпоинт 768px), тёмная тема через `prefers-color-scheme`, весь CSS в одном файле.

Первая в очереди на отсечение. Если сессии не будет — в `REPORT.md` строка о том,
что UI остался функциональным, но неполированным, и почему.

Финальный шаг независимо от объёма: проверка на секреты и упоминания работы
(правило 6 `CLAUDE.md`), финальный push.

## Необязательное, взятое как опция

### Visual regression — ❌ решено не брать

**Решение принято пользователем 23 августа 2026**, см. `D-02` в `decisions.md`.

Рассматривали: отдельный проект в `playwright.config.ts`, только `macos-latest`,
исключён из матрицы. Отказались: baseline снимался бы с вёрстки, которую мы сами пишем
в таймбоксе 45 минут в последней сессии, — такой тест ловит почти исключительно
собственные правки, а риск флаки от разного рендеринга шрифтов реален.

Отказ с обоснованием идёт строкой в `REPORT.md`: рассматривали, отказались, вот почему.
Это лучше молчания.

### Git worktrees — ✅ взяты, двумя заходами

**Статус изменён.** Были «если останется время», стали частью работы:

- **S3** — worktree скептика без `src/` в рабочей копии. Здесь worktree решает задачу,
  которую промптом не решить: превращает «не читал реализацию» из обещания в свойство
  файловой системы;
- **S4** — три ветки (`e2e`, `workflow`, `docs`), три агента, merge в `main` руками
  пользователя. Это буквальный сценарий из задания.

Чистка в обоих случаях — в том же шаге, что и завершение работы, с выводом
`git worktree list`.

### Прежняя формулировка (оставлена для истории)

**Не обязательство.** Место — буфер после S6 или суббота.

Раскладка на три области проверок: (1) базовый аннуитет, (2) досрочное погашение,
(3) страховка и валидация. Три ветки, три агента, merge вручную пользователем.

**Чистка — сразу в плане, не потом:**

```
git worktree remove ../wt-<name>
git worktree prune
git worktree list
```

Три worktree = три `node_modules`. В материалах занятия описан случай, когда так
накопилось 250 ГБ. Удаление — в том же шаге, что и merge, а не «когда-нибудь».
