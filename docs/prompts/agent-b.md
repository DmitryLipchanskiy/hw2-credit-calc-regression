# Агент B — эталонная реализация на Python

**Зона:** `oracle/**` и ничего больше.

Смысл зоны: вторая, независимая реализация тех же формул, на другом языке, другим автором.
Совпадение TS и Python на сотнях случайных входов — кросс-проверка. Она ловит ошибки
реализации, но **не** ловит ошибки спецификации: обе стороны читают один документ.
От этого страхует только `docs/oracle.md`.

---

## Промпт (передаётся субагенту целиком)

```
Ты пишешь эталонную реализацию расчёта кредита на Python. Работаешь один, параллельно
с тремя другими агентами.

## Твоя зона

Только каталог oracle/. Создавать и менять файлы можно исключительно там.

Тебе ЗАПРЕЩЕНО:
— читать и менять src/** — там параллельно пишется реализация на TypeScript;
— читать и менять tests/**;
— трогать docs/**, sessions/**, README.md, REPORT.md, конфиги в корне.

Запрет на чтение src/** — не формальность, а весь смысл твоей работы. Ты нужен именно
как независимая реализация. Если ты подсмотришь в TypeScript-код, эталон превратится
в его перевод и перестанет что-либо доказывать. Даже если код попадётся тебе на глаза
случайно — скажи об этом в отчёте.

## Источник истины

docs/spec.md — требования REQ-01…REQ-38, инварианты INV-01…INV-08.
Раздел 9 (REQ-38) задаёт контракт. Воспроизведи ту же структуру данных в snake_case:
payment_total, early_repayment_applied, total_insurance и так далее. Состав полей
и их смысл менять нельзя — по ним пойдёт механическая сверка.

Если спецификация в чём-то неполна — НЕ додумывай, зафиксируй вопрос в отчёте
и реализуй наиболее буквальное прочтение.

## Что сделать

1. oracle/calculator.py — функция calculate_credit(input_dict) -> dict,
   реализующая REQ-01…REQ-27 и REQ-36…REQ-37. Возвращает либо
   {"ok": True, "schedule": [...], "totals": {...}},
   либо {"ok": False, "errors": [...]}.

2. oracle/compare.py — скрипт сверки. На вход два JSON-файла (результат TS и результат
   Python), на выход — список расхождений по каждому полю каждой строки графика
   и каждому итогу.

3. oracle/cases.json — набор входных параметров для сверки: не менее 200 случаев.
   Включи и типовые, и граничные: минимальная и максимальная сумма, срок 1 и 360,
   ставка 0 и 100, суммы, не кратные копейке при делении, досрочки на первом
   и на последнем месяце, страховка на длинном сроке.

## Жёсткие требования

1. Все денежные величины — целые числа копеек (int). Никаких float для денег.
   ВАЖНО: в Python нет автоматического приведения, но есть деление / , которое
   возвращает float всегда. Используй целочисленные операции осознанно.
2. Плавающая точка допустима ТОЛЬКО для месячной ставки i и коэффициента K (REQ-03).
3. Округление — half-up, до целых копеек (REQ-04). ВНИМАНИЕ: встроенная round()
   в Python использует банковское округление к чётному: round(2.5) == 2.
   Это НЕ то, что нужно. Реализуй half-up явно, например через decimal.Decimal
   с ROUND_HALF_UP. Проверь: 1.5 → 2, 2.5 → 3, 1.4999 → 1.
4. Ветка нулевой ставки — строго при annual_rate_percent == 0 (REQ-13).
5. Сравнения денег в compare.py — строгое равенство целых чисел. Допуски запрещены:
   ни math.isclose, ни abs(a-b) < eps, ни округления перед сравнением (REQ-36).
   Расхождение в копейку — именно то, что мы ищем.
6. Только стандартная библиотека Python. Без numpy, без pandas.
7. Код должен работать на Python 3.9 и новее — на машине разработчика 3.9.6,
   в CI ставится через actions/setup-python. Не используй синтаксис новее 3.9
   (например, match/case из 3.10 или | в аннотациях типов из 3.10).

## Чего делать НЕЛЬЗЯ

— Писать тесты для TypeScript-кода: ты пишешь эталон, а не проверки.
— Подгонять свой результат под чужой.
```

## Заметки для главной сессии

- Python 3.9.6 на машине — проверено командой в сессии 1. Ограничение по синтаксису
  в промпте не теоретическое: `X | None` в аннотациях упадёт.
- `compare.py` понадобится в шаге 2 S2 для CI — он и есть кросс-проверка на матрице.
- Если Python и TS разойдутся, первым делом проверяется **округление**: `round()`
  в Python и `Math.round()` в JS ошибаются по-разному, и это самый вероятный источник
  расхождения в копейку.
