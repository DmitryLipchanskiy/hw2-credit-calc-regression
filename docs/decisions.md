# Журнал решений

Файл **только дописывается**. Записи не редактируются и не удаляются: если решение
оказалось неверным, добавляется новая запись с отменой, а старая остаётся.

Обязательные поводы для записи:

- **изменение ожидаемого значения в тесте** — только со ссылкой на `REQ-NN` из
  [spec.md](spec.md) или на строку [oracle.md](oracle.md) (правило 4.6 в `CLAUDE.md`);
- изменение самой спецификации;
- отказ от запланированного объёма работ;
- тупик, о котором остановились и сказали вслух (правило 4.7).

Формат записи:

```
## D-NN · <дата> · <короткий заголовок>

**Что было:**
**Что стало:**
**Основание:** REQ-NN / O-NN / прямое решение пользователя
**Кто:** главная сессия / агент N / скептик / аудитор
```

## D-01 · 2026-08-23 · Плавающая точка допущена в одном месте

**Что было:** требование пользователя — «все денежные величины внутри модуля хранить
целыми числами в копейках, никаких float в расчётах».

**Что стало:** REQ-01, REQ-02 фиксируют целые копейки для всех денежных величин.
REQ-03 допускает `float` **только** для месячной ставки `i` и безразмерного аннуитетного
коэффициента `K`, с немедленным округлением результата умножения до целых копеек.

**Основание:** аннуитетный коэффициент содержит `(1 + i)^n` и иррационален.
Полностью целочисленный расчёт потребовал бы длинной рациональной арифметики,
что противоречит требованию «SUT остаётся намеренно простым». Ограничение вынесено
в `REPORT.md` как сознательное сужение.

**Кто:** главная сессия, сессия 1, согласовано с пользователем до написания кода.

## D-06 · 2026-08-23 · REQ-13: граница ветвления нулевой ставки

**Что было:** «при `annualRatePercent === 0` формула REQ-12 неприменима».

**Что стало:** явно записано, что ветка выбирается **строго** при `=== 0`; условия вида
`rate < 0.01`, `rate <= 0`, `!rate` названы ошибкой. Добавлен парный кейс: 0 % и 0,01 %.

**Основание:** требование пользователя — классическое место для off-by-one в условии.

**Побочная находка при внесении правки.** Пользователь предложил как граничный кейс
ставку 0,0001 %. Такой вход **невалиден** по REQ-06: разрешено не более двух знаков
после запятой, вход отвергается кодом `RATE_TOO_PRECISE`. Минимальная ненулевая ставка,
которую вообще можно подать, — **0,01 %**; она и взята граничным кейсом. Ограничение
записано врезкой в REQ-13. Расширять точность ставки — отдельное решение, требующее
правки REQ-06.

**Кто:** пользователь (требование), главная сессия (находка про 0,0001 %), сессия 1.

## D-11 · 2026-08-23 · Личный email убран из репозитория, переход на noreply

**Что было:** при проверке на секреты перед вторым коммитом (правило 6 `CLAUDE.md`)
в `sessions/session-1.md` обнаружен личный email пользователя. Он попал туда из блока
проверки окружения — я записал вывод `git config --global user.email` дословно.
Репозиторий публичный.

**Что стало, в три шага:**

1. **Содержимое.** Адрес заменён на плейсхолдер `<личный email, скрыт>`, коммит
   переписан через `git commit --amend` — адреса нет не только в рабочем дереве,
   но и в истории. Проверено:
   `git log -p --all | grep -E "^[+-].*<адрес>" | wc -l` → `0`.
   Старый коммит остался dangling в reflog; вычищается `git gc --prune` перед push.
2. **Метаданные автора.** Локальная (не глобальная) идентичность репозитория + переписывание
   обоих коммитов:
   `git rebase --root --exec "git commit --amend --no-edit --reset-author"`.
   Ожидает точный noreply-адрес от пользователя. **Выполняется до первого push.**
3. Остальные проекты пользователя не затрагиваются: идентичность ставится локально.

**Основание:** репозиторий публичный, адрес в метаданных каждого коммита остаётся там
навсегда и собирается ботами. Решение пользователя.

**Нарушение правила «журнал только дописывается» — осознанное.** Правило 5 `CLAUDE.md`
запрещает править `sessions/`. Здесь оно нарушено намеренно: цена соблюдения —
навсегда опубликованный личный адрес. Нарушение зафиксировано этой записью и строкой
в `REPORT.md`, а не проведено молча. Заменено ровно одно вхождение, содержательная часть
журнала не тронута.

**Кто:** обнаружено главной сессией при обязательной проверке, решение пользователя,
сессия 1.

## D-13 · 2026-08-23 · REQ-38: публичный контракт фиксируется спецификацией

**Что было:** спецификация описывала поведение, но не сигнатуры. Предполагалось, что
структуру типов определит агент A вместе с реализацией.

**Что стало:** REQ-38 — раздел 9 `spec.md` с полным контрактом: `CreditInput`,
`ScheduleRow`, `CreditTotals`, `CalculationResult`, `calculateCredit`, `roundHalfUp`,
перечисление `ValidationCode`. Контракт одинаков для агентов A, B, C и D.

## D-14 · 2026-08-23 · Правило точности ставки само должно быть проверено

**Что стало:** в зону агента C добавлены два кейса:

## D-15 · 2026-08-23 · Ожидаемые значения разведены на два уровня

**Что было:** промпт агента D предлагал «строить кейсы на коротких сроках, где график
можно посчитать полностью и вписать ожидаемые значения по месяцам».

**Что стало:** в промптах C и D ожидания разведены на два уровня.

- **Уровень 1 — свойства и отношения, без точных чисел.** Большинство кейсов.
  Платёж после `reducePayment` строго меньше прежнего; число строк уменьшилось;
  `principal`/`interest` совпадают построчно в паре кейсов со страховкой и без;
  `applied + excess === requested`; поля целые. Такие проверки не могут «почти сойтись».
- **Уровень 2 — точные числа, мало и только с якорем.** Допустимы, только если значение
  взято из `oracle.md` (со ссылкой на `O-NN` в комментарии) или считается в одну
  операцию. Помесячные таблицы, посчитанные агентом, запрещены — на любой длине.

Плюс жёсткое правило: **не уверен в числе — не вписывай.** Кейс переводится на уровень 1
либо не пишется вовсе и попадает в отчёт в раздел «требует якоря».

**Основание:** требование пользователя, и оно снимает главный риск веера. Модель,
считающая аннуитет до копейки, выдаёт правдоподобные неверные числа. Красная фаза при
этом проходит честно, зелёная не сходится — и время уходит на поиск несуществующего бага
в исправном коде.

**Где на самом деле ловится копейка:** не в ручных кейсах, а в `oracle/compare.py` —
автоматической сверке 200 случаев TS ↔ Python. Ручные кейсы нужны для смысла,
а не для объёма.

**Кто:** пользователь, сессия 1.

## D-17 · 2026-08-23 · `as unknown as` в тестах скрыл перепутанные аргументы

**Что было:** агент D не мог прочитать `tests/core/invariants.ts` (зона агента C) и не знал
сигнатуру `checkInvariants`. Он застраховался приведением
`checkInvariants as unknown as (result, input?) => void` и вызвал `(result, source)`.
Агент C объявил `(input, result)` — порядок обратный.

**Как проявилось:** красная фаза этого **не поймала** — тесты D падали и от `NotImplemented`,
и от перепутанных аргументов, вывод одинаковый. В зелёной фазе все 73 теста C прошли,
все 67 тестов D упали с `Received: undefined` — в позицию `result` попадал `CreditInput`.

**Что стало:** приведение убрано, вызов `assertInvariants(source, result)`, порядок исправлен.
Заодно убрано второе приведение — на самом `calculateCredit`. Оно оказалось не нужно:
локальная транскрипция контракта у D структурно совпадает с REQ-38, и прямой вызов
компилируется. Это побочно подтверждает корректность REQ-38.

**Следствие:** `as any` и `as unknown as` внесены в запрещённые приёмы pre-commit hook
(`CLAUDE.md`, 4.5) с одним документированным исключением — тесты валидации, намеренно
передающие значение неверного типа.

**Кто:** дефект — агент D; обнаружено и исправлено главной сессией при сведении, сессия 2.

## D-33 · 2026-08-24 · Правило двух уровней ослабило набор веера — измерено

**Что измерено.** Девять мутаций скептика прогнаны по трём наборам:

| Набор | Поймал |
|---|---|
| 49 тестов последовательной сессии | **6 из 9** |
| 140 тестов веера, до правок | **1 из 9** |
| 160 тестов веера, после правок | 9 из 9 |

**Причина — правило `D-15`, введённое нами.** Агентам C и D было запрещено вписывать
точные числа без внешнего якоря; большинство их кейсов — отношения. Правило сработало
как задумано: ни одного неверного числа в наборе не появилось. И оно же лишило набор
способности ловить ошибки в величинах — отношение «платёж 13 меньше платежа 12» истинно
и при верном платеже, и при заниженном на тысячу рублей.

Последовательная сессия этого запрета не получала (её промпт написан раньше `D-15`),
считала значения помесячно и вписывала числами. Риск не реализовался: все 49 её тестов
проходят на нашей реализации, написанной другим агентом.

**Что из этого следует и что не следует.**

Не следует, что `D-15` был ошибкой: неверное правдоподобное число стоило бы суток
отладки, а якорей на тот момент не было. Следует, что правило было **неполным** —
запрет на числа без якоря обязан сопровождаться требованием добыть недостающие якоря
до начала работы. O-05, O-06, O-09, O-10 вычислены через `FV`/`PMT` за пятнадцать минут
уже постфактум; их можно было посчитать до веера.

**Практическое правило на будущее, если понадобится:** прежде чем запрещать агенту
точные значения, посчитай, во что обойдётся их добыть. Пятнадцать минут в `oracle.md`
дешевле, чем набор, который ничего не ловит.

**Кто:** измерение — главная сессия по требованию пользователя, сессия 3.

## D-34 · 2026-08-24 · Селекционное смещение в сравнении наборов; прогнана обратная половина

**Что было не так.** Первое сравнение наборов строилось на девяти мутациях, из которых
восемь — ровно те, что **не поймал веер**. Их отобрал скептик, работавший по набору веера,
именно как его провалы. Вывод «wave-156 поймал 1 из 9» при такой выборке почти
тавтологичен: список составлен из его слабостей, а слабости `seq-49` в него попасть
не могли. Дыру нашёл пользователь до публикации вывода.

**Что сделано.** Прогнаны десять мутаций из числа **пойманных** веером, по обоим наборам.

| | из «слепых зон веера» (9) | из «пойманного веером» (10) | всего (19) |
|---|---|---|---|
| seq-49 | 6 | **10** | **16** |
| wave-156 | 1 | 10 | 11 |

Не воспроизведены две (M-08, M-15) — требуют структурной правки, а не замены строки.

**Исход:** первый из трёх, названных пользователем. Набор из 49 тестов — **надмножество**
по обнаружительной способности: ловит всё, что ловит набор из 140, плюс пять дефектов,
которые тот пропускает. Мутаций, которые поймал бы только веер, не нашлось.

сильнее **на проверенном наборе дефектов**.

**Уточнение к `D-33`, которое от этого не зависит:** риск неверных рукописных чисел
не реализовался **в одной попытке**. Это не доказательство, что его нет.

**Кто:** дыру нашёл пользователь; прогон и записи — главная сессия, сессия 3.

## D-35 · 2026-08-24 · Тег `last-run` остаётся локальным и не пушится

**Вопрос:** тег `last-run`, которым workflow-скилл отмечает проверенную точку, —
общерепозиторный. Пушить ли его в remote?

**Решение: не пушить. Тег локальный.**

**Основание.** Тег отвечает на вопрос «что проверено **на этой машине**». Если он уедет
в remote, свежий клон получит метку прогона, которого на той машине не было: первый же
запуск скилла возьмёт чужую базу, увидит «изменений с прошлого раза нет» и прогонит
только smoke — вместо полного прогона, который на новой машине как раз и нужен.

Отсутствие тега скрипт обрабатывает штатно: база определяется как последний коммит main,
и это осознанно консервативный выбор — «не знаю → проверяю всё».

**Побочное следствие merge.** После слияния трёх веток тег указывал на `209295d` —
коммит ветки `workflow`, которого в линейной истории main нет. Переставлен на текущий
main вручную. Это разовая операция: в дальнейшем тег двигает сам скрипт.

**Что сделано механически:** ничего. `git push` без `--tags` теги не отправляет,
дополнительная защита не нужна — нужна запись, чтобы никто не добавил `--tags`
«для порядка».

**Кто:** вопрос поднял агент workflow в отчёте, решение — главная сессия, сессия 4.

## D-37 · 2026-08-24 · Номер записи вычисляется из файла, а не назначается по памяти

**Что было:** дважды номер новой записи назначался по памяти и сталкивался

grep -o '^## D-[0-9]*' docs/decisions.md | sort -V | tail -1

grep -o '^## D-[0-9]*' docs/decisions.md | sort | uniq -d
