# Изоляция: что проверено и что проверить не удалось

Сессия 5, 24 августа 2026. Материал для `REPORT.md`.

Задание просит не «запускал в песочнице», а **вывод неудачной попытки** выйти за
границу. Такой вывод получен — ниже дословно.

**Сразу о границах эксперимента.** Проверен **системный Seatbelt** (`sandbox-exec`),
то есть механизм, который лежит под встроенной песочницей Claude Code. Сама встроенная
песочница и обход через MCP-сервер **не проверялись** — почему, сказано в конце
документа, и этот раздел стоит читать наравне с результатами.

---

## Чем проверялось

Встроенная песочница Claude Code включается командой `/sandbox` в сессии — это действие
человека, агент её включить не может. Поэтому граница проверялась **тем же системным
механизмом**, на котором построена эта песочница: `sandbox-exec` (Seatbelt, macOS).

Профиль — [`workdir-only.sb`](workdir-only.sb): запись разрешена только внутрь каталога
проекта, чтение и запуск процессов не ограничены. Это делает проверку воспроизводимой
и не зависящей от того, включена ли песочница сессии.

```
sandbox-exec -f docs/isolation/workdir-only.sb \
  -D WORKDIR=<путь к репозиторию> /bin/sh -c '<команда>'
```

---

## Базовая линия: без песочницы граница отсутствует

Зафиксировано **до** включения ограничений, иначе не с чем сравнивать:

| Что пробовали | Результат |
|---|---|
| запись в `~/Documents` | **удалась** |
| чтение `~/Downloads` | **удалось** |
| сеть, `https://example.com` | **HTTP 200** |

## Внутри границы: работает

```
$ sandbox-exec -f workdir-only.sb -D WORKDIR=<repo> /bin/sh -c \
    'echo ok > ./sandbox-probe-inside.txt && cat ./sandbox-probe-inside.txt'
запись удалась:
ok
```

Профиль не ломает нормальную работу — это важно, иначе «отказ» ничего не доказывает.

---

## Попытки выйти: четыре отказа

Все четыре — дословный вывод команды, не пересказ.

### 1. Запись в домашний каталог

```
$ sandbox-exec ... /bin/sh -c 'echo escaped > /Users/<user>/Documents/claude-escape.txt'
/bin/sh: /Users/<user>/Documents/claude-escape.txt: Operation not permitted
exit: 1

файл создан? нет — граница удержала
```

### 2. Запись в `/tmp`

```
/bin/sh: /tmp/claude-escape.txt: Operation not permitted
exit: 1
```

### 3. Дозапись в чужой конфиг

```
/bin/sh: /Users/<user>/.zshrc: Operation not permitted
exit: 1
```

### 4. Удаление файла вне каталога

```
rm: /Users/<user>/.viminfo: Operation not permitted
exit: 1
```

Отдельно отмечено: попытка вытащить те же отказы из системного лога
(`log show --predicate 'senderImagePath CONTAINS "Sandbox"'`) вернула пустой результат —
предикат не подошёл либо нужны дополнительные права. Копать дальше не стали: отказы уже
получены от самих команд, и это первичный источник. **Неудавшаяся попытка записана,
а не скрыта.**

## Что проверить НЕ удалось

Этот раздел важнее предыдущего. Задание предлагало два артефакта, получен один.

### 1. Встроенная песочница Claude Code — не проверялась

`/sandbox` — интерактивная команда сессии, её выполняет человек. Агент включить её
не может, и в этой среде терминальные диалоги недоступны.

Проверено **не** то, что предлагало задание: вместо встроенной песочницы взят системный
механизм, на котором она построена. Это честный способ показать границу, но это
**другой объект проверки**. Формулировка «агент работал в песочнице Claude Code» была бы
неверной и здесь не используется.

### 2. Обход через MCP — не воспроизведён

Материалы предупреждают: встроенная песочница «применяется только к Bash-командам и их
дочерним процессам», а MCP-серверы под неё не попадают. Сюжет в том, что **сессия целиком**
работает под ограничением, а подключённый MCP-сервер остаётся снаружи и дотягивается
туда, куда терминалу уже нельзя.

**На `sandbox-exec` этот сюжет не воспроизводится.** Здесь под профиль попадает один
конкретный процесс, запущенный командой `sandbox-exec`, а не сессия. Всё остальное —
включая любые инструменты агента — никогда под ним и не было.

Проба, которая это показывает, проведена и приводится ниже, но **как иллюстрация
устройства, а не как обход защиты**:

```
# терминалу под профилем отказано
$ sandbox-exec -f workdir-only.sb -D WORKDIR=<repo> /bin/sh -c \
    "echo 'written by sandboxed bash' > <scratchpad>/probe.txt"
/bin/sh: <scratchpad>/probe.txt: Operation not permitted
exit: 1

# файловый инструмент агента пишет туда же
-rw-r--r--@ 1 <user> wheel 81 <scratchpad>/probe.txt
```

Назвать это «пробили песочницу через MCP» было бы натяжкой, и первая редакция этого
документа именно так и делала — формулировка исправлена после замечания. Разница
существенна:

| | Сюжет из материалов | Что сделано здесь |
|---|---|---|
| Под ограничением | вся сессия агента | одна команда `sandbox-exec` |
| Снаружи оказывается | MCP-сервер, не наследующий песочницу | процесс, который под профилем и не запускался |
| Ценность вывода | защита обходится в реальной конфигурации | почти тавтология: профиль действует на тот процесс, к которому применён |

Кроме того, MCP-серверов с правом записи на файловую систему в этой сессии подключено
не было, так что проверить нечего и с этой стороны.

**Что осталось непроверенным, названо непроверенным.** Натянутое «проверили» стоило бы
меньше, чем честно очерченная граница эксперимента.

Обе пробы удалены сразу после снятия вывода.
