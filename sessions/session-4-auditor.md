### F-1. Набор тестов не замечает семь поломок ядра из тридцати пяти. Две из них не замечает и кросс-проверка

Внесено 35 поломок по одной, с откатом между ними. Базовая линия перед началом —
`168 passed`, рабочее дерево чистое. Полная таблица — в приложении.

Почему это важно. REQ-10 явно фиксирует **порядок** кодов ошибок — и порядок не закреплён
ни одной проверкой; тесты сверяют состав списка, а `toEqual` на массиве из двух кодов
случайно совпал с порядком только для тех пар, которые кто-то догадался проверить.

требование живёт в коде, — константа допуска, и её можно ослабить на пять порядков,
не уронив ничего. Оба контура молчат.

Отдельно: пять уцелевших в наборе поломок ловятся кросс-проверкой ровно в **одном-двух**
кейсах из 290. Запаса нет: удаление одного случая из `cases.json` превращает их
в невидимые. Это то же наблюдение, которое `docs/mutations.md` делает про свои
M-13 и M-18 («держатся одним тестом каждая»), только на границах валидации,
где авторы его не сделали.

### F-2. `docs/mutations.md` строит вывод на факте, который не был верен ни при написании, ни сейчас

Документ утверждает (раздел «Мутации, не пойманные ни одним контуром»):

и повторяет «не ловит» в итоговой таблице для M-04, M-05, M-06.

Проверено воспроизведением тех же трёх поломок на текущем HEAD:

| Их мутация | Правка | Набор | Кросс-проверка |
|---|---|---|---|
| M-04 | `insuranceRate > MAX` → `>=` | 2 failed | **расхождения в 5 кейсах** |
| M-05 | `term < TERM_MIN` → `<=` | 3 failed | **расхождения в 14 кейсах** |
| M-06 | `month > termLimit` → `>=` | 1 failed | **расхождения в 5 кейсах** |

Числа не случайны — они точно равны числу соответствующих входов в `cases.json`:

```
termMonths == 1:                     14 кейсов
страховка ровно 10 %:                 5 кейсов
досрочка в месяц termMonths:          5 кейсов
```

И это не следствие более поздней доработки набора случаев:

```
$ git log --oneline -- oracle/cases.json
32a9ffb feat(oracle): add independent Python reference and 290-case cross-check
$ git log --oneline -- docs/mutations.md
99b2c90 test: close the eight coverage holes the skeptic found
```

`cases.json` имеет ровно один коммит, сделанный **раньше** `mutations.md`. Утверждение
было ложным в момент написания. Тезис «это настоящие дыры, не пойманные ни одним
контуром» завышает тяжесть собственных находок: второй контур ловил их всё это время.
Проверка, которую документ описывает как выполненную, выполнена не была — иначе
расхождения увидели бы.

README перечисляет команду в общей таблице без единого слова о порядке. При проходе

и никакого объяснения.

### F-4. `npm run lint:forbidden` рапортует «clean», не посмотрев на новый файл

```
$ cat > tests/core/tmp-audit-probe.spec.ts   # test.only + expect(true).toBe(true)
$ npm run lint:forbidden
forbidden-pattern check: 21 file(s) clean
$ echo $?
0
```

Причина — `scripts/check-forbidden.mjs` отбирает файлы через `git ls-files`, то есть
видит только отслеживаемые. Стоит сделать `git add` — та же команда падает с кодом 1
и печатает все четыре нарушения. То есть инструмент слеп ровно в тот момент, когда
он нужнее всего: файл написан, ещё не добавлен, автор гоняет проверку локально.

Хуже самого пропуска — формулировка. «21 file(s) clean» — утверждение о чистоте,
а не о том, что проверено 21 из 22 существующих. В истории репозитория есть два
коммита именно про этот класс ложной зелени (`fix: never report zero checked files
as clean`, `fix: say precisely why there was nothing to check`) — дыру рядом
с ними не закрыли.

Сам pre-commit хук отрабатывает корректно: код возврата 1, все четыре приёма названы
с номерами строк.

## 3. Сверка с `docs/mutations.md`

### Что нашёл я, чего в их таблице нет

Все семь поломок, уцелевших в наборе, — новые относительно их таблицы, и три из них
лежат в направлении, которое скептик не проверял вовсе.

- **Обратная граница страховой ставки (M16, M33, M30).** Их M-04 ломает границу
  в сторону «отвергнуть валидное» (`>` → `>=`, ставка ровно 10,00 % перестаёт
  приниматься) — и после починки ловится. Я ломал ту же границу в другую сторону:
  `MAX = 10.01`, `MAX = 10.5`, `MIN = -1`. Ставка 10,005 % и отрицательная ставка
  проходят валидацию, набор остаётся зелёным. Починка закрыла одну сторону границы
  из двух, и таблица этого не отмечает.
- **Порядок кодов REQ-10 (M17, M34).** Их M-15 проверяет, что возвращается больше
  одного кода. Что коды возвращаются в **порядке таблицы REQ-09** — не проверяет
  никто. M34 не ловится ни одним контуром.
- **Допуск в `hasMoreThanTwoDecimals` (M18, M35).** В их таблице отсутствует
  как класс. Ослабление на пять порядков невидимо для обоих контуров.
- **F-2** — их собственное утверждение про `cases.json`, опровергнутое прогоном.

### Что есть в таблице, а я пропустил

Честно: заметная часть, и вся — в одном направлении.

- **Мутации вида «граница отвергает валидный вход»** (их M-04, M-05, M-06).
  Я ломал границы почти исключительно наружу — расширял диапазон, чтобы проходил
  невалидный вход (M15, M24, M25, M26, M27, M36). Сужение диапазона, при котором
  отвергается валидный `termMonths = 1` или досрочка в последний месяц срока,
  мне в голову не пришло вообще. Это ровно та асимметрия, которую они описывают
  в разделе про знак, — только у меня она в валидации, а у них в амортизации.
- **Округление страховой премии** (их M-01). Я ломал округление процентов (M20)
  и общий `roundHalfUp` (M01), но не третье место, где округление применяется.
- **Округление в ветке нулевой ставки** (их M-22). Я трогал только границу
  ветвления (M06), не содержимое ветки.
- **Сдвиг пересчитанного платежа на константу** (их M-10, M-11). Я сделал сдвиг
  числа периодов (M05), не сдвиг суммы. Их вариант тоньше: он не меняет длину
  графика и до починки поглощался корректирующим последним платежом.
- **База страховки: остаток → первоначальная сумма** (их M-21).
- **Валидация возвращает только первый код** (их M-15).

Их разбор асимметрии знака в `reducePayment` — содержательно сильнее всего, что нашёл
я в области расчёта. Мой вклад целиком лежит в валидации, куда они почти не смотрели,
и это симметричная слепота: они разобрали арифметику и пропустили границы,
я разобрал границы и пропустил половину арифметики.

Два эквивалентных мутанта, названных ими (`rate / 1200` и `zeroRate = rate < 0.01`),
я не проверял — первый отбросил как заведомо эквивалентный на этапе составления
списка, до чтения их таблицы.

## 4. Вердикт по критерию задания

**Запускается ли результат по инструкции, без «допишите тут своё»? — Да.**

Обоснование. «Минимальный сценарий проверяющего» из README — четыре команды —
на чистом клоне отрабатывает начисто и даёт ровно заявленные числа:

```
npm ci                          -> 92 пакета, хук включён через prepare
npx playwright install chromium -> браузер на месте
npm test                        -> 168 passed
npm run cross-check             -> 290 кейсов, расхождений нет
```

Ни одной догадки, ни одной доустановки, ни одного правленого пути. Все 15 команд
из обеих таблиц README существуют и выполняются.

Оговорки, которые не отменяют «да», но обязаны прозвучать:

1. Дословный проход README сверху вниз даёт **один красный шаг** — `ci:evidence`
   с кодом 1 (F-3) — и **один шаг, на который сам инструмент ругается** —
   установка браузера до `npm ci` (F-6). Оба обходятся без вмешательства
   в проект, но проверяющий, идущий по документу буквально, увидит красное.
2. `npm run check:secrets` работает, но найти его по README нельзя (F-9).

Что «да» не означает. Запускаемость — не то же самое, что доказанная корректность.
Набор из 168 тестов не замечает семи поломок ядра, две из которых не замечает и
кросс-проверка (F-1), а workflow при правке ядра второй контур не поднимает (F-5).
Проект запускается по инструкции; заявление же, что он проверен, для `validate.ts`
держится слабее, чем следует из README и из `docs/mutations.md`.
